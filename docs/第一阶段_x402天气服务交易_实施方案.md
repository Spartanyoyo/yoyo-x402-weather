# 第一阶段实施方案：Codex 通过 x402 购买云端天气服务

**提交用途：依据 mentor 回复更新，作为第一阶段的实施与验收方案。**
**日期：2026 年 10 月 16 日｜版本：F-01／F-02 文档驱动调用修订版**
**当前状态：第一阶段技术流程已于 2026 年 10 月 16 日完成。Codex 已读取云端 F-02，通过自有天气服务完成北京查询、HTTP 402 → 支付 → 200，并独立核对买方扣款和卖方到账。最终结果与 A1–A10 证据见 [验收报告](第一阶段_验收报告.md)，状态见 [STATUS](STATUS.md)。**

**已确认的选型条件：**天气接口、云平台和测试链均无指定要求，以方便接入、部署和验证为优先。Finch 仅用于参考 API 请求格式，不是必须接入的系统组件，也不作为验收依赖。

**一、任务理解与预期成果**

第一阶段拟完成一个可以实际演示的交易流程：用户用自然语言提出具体天气查询需求，Codex 先阅读我们编写的云端服务 API 文档 F-02，再把需求转换为服务接受的明确参数，通过 x402 买方工具请求我们部署的云端天气服务。服务先返回付款要求，买方使用专用测试钱包完成支付流程，服务随后向买方交付真实天气数据。最后通过链上交易、代币转账记录和双方余额证明买方付款、卖方到账。

卖方是收到请求后按规则响应的程序，暂不需要自主推理、规划或协商能力。买方工具和卖方服务分别配置；复用官方买方示例，仍然需要我们搭建自己的云端卖方服务。[1][2]

本阶段的交付重点是：**我们自己的服务地址、真实天气接口接入、可供 Codex 阅读的 F-02 文档、x402 收费配置、自然语言需求到 API 请求的调用过程，以及可复核的测试网交易证据。**

**二、第一阶段的输入与范围**

本阶段区分两层输入：用户与 Codex 之间使用自然语言；Codex 与云端服务之间使用符合 F-02 的 API 请求。用户无需了解请求格式，也不必主动提供经纬度。mentor 提供的 RapidAPI 天气接口作为候选参考，不要求必须使用。

例如，我们可能给 Codex 一条这样的操作指令：

> 请通过我们部署的天气服务查询上海现在的天气，在约定测试币额度内完成支付，并给出天气结果和付款证据。

Codex 每次开始调用云端天气服务前，先读取 F-02，核对服务入口、参数、支付与返回格式，再组织请求。具体参数名、取值格式、请求方法和路径以 C 实际实现及 F-02 为准；不要求用户把它们写进自然语言指令。

需要明确地点转换路径：优先选择便于接受地名的接口；如果 C 只接受经纬度，则在 F-02 中说明如何通过已配置的地点查询工具或有来源的地点资料取得坐标。必要信息不足或地点有歧义时由 Codex 向用户询问，不能臆造坐标，也不能假设一份文档能够代替实际缺失的工具。验收记录同时保存用户原话和最终 HTTP 参数，以验证两者对应。

| 本阶段纳入 | 本阶段暂不纳入 |
|---|---|
| 自然语言天气需求、按 F-02 组织参数、真实上游响应 | 面向任意模糊地点的复杂地理推理系统 |
| F-01 上游接入依据、我们编写且可访问的 F-02 | 强制安装 Skill 或额外搭建 MCP 服务 |
| 买方与卖方两个测试钱包 | 主网和真实资金支付 |
| 我们部署的 x402 天气服务 | 多 Agent 自主议价、任务协商 |
| 402 付款要求、支付处理、天气交付 | 自行开发支付协议、签名算法或智能合约 |
| 云端访问与链上收付款验收 | 完整交易平台、复杂前端、市场上架 |

F-02 是本阶段必须交付的接口说明，可以放在服务器可访问的文档地址，也可以作为本地文件由用户提供给 Codex。README 可以承载说明；Skill 可在后续用于复用调用流程。文档可访问、内容准确且调用前实际阅读是完成条件，创建 Skill 或接入 MCP 不是前置要求。第二、第三阶段内容留待 mentor 明确。

**三、系统由哪些部分组成**

```text
A：用户用自然语言提出天气查询需求
          ↓
B：Codex 先阅读 F-02，再通过现成 x402 客户端组织请求
          ↓ 发出请求／提交支付凭证
C：我们部署在云端的天气服务
  ├─ 对外接口与参数转发
  ├─ x402 付款要求、价格和收款地址
  ├─ 调用现成支付验证与结算服务 → 测试链
  └─ 根据 F-01 接入 D：原始天气 API → 返回天气数据
```

| 部分 | 作用 | 本项目如何处理 |
|---|---|---|
| 用户（A） | 用自然语言提出具体查询需求 | 无需掌握 C 的参数格式；必要时补充地点等信息 |
| Codex（B） | 阅读 F-02，将需求转换为请求，调用工具、记录过程和解释结果 | 在当前本机工作环境中作为买方操作入口 |
| x402 买方客户端 | 读取付款要求，调用钱包签名，携带支付凭证重试 | 优先复用官方示例或 SDK，目标地址配置成我们的云端接口。[1][4] |
| 云端天气服务（C） | 对外提供收费接口，连接天气上游和支付组件 | 由我们配置、部署和维护，并编写其 F-02 文档 |
| 原始天气 API（D） | 提供真实天气数据及 F-01 接口文档 | 按接入便利性选择；我们根据 F-01 实现 C 到 D 的接入 |
| x402 支付组件 | 生成付款要求、验证支付流程并控制资源交付 | 复用官方中间件或现成网关，避免重写协议。[2][5] |
| 支付结算服务（facilitator） | 验证买方授权并提交链上结算 | 使用与所选测试网、协议版本匹配的现成服务。[3] |
| 两个测试钱包 | 分别代表买方付款地址与卖方收款地址 | 使用不同地址，便于核对双方余额 |
| 区块浏览器 | 展示交易状态、地址和代币转账 | 使用所选测试链对应的浏览器 |

云端部署的是我们包装好的服务入口与支付接入层；天气数据仍向上游 API 请求。买方客户端可以在本机运行，不要求将 Codex 也部署到云端。这是本方案的部署安排。

**F-01 与 F-02 的职责**

| 文档 | 编写者 | 谁使用、解决什么问题 |
|---|---|---|
| F-01：原始天气 API 文档 | D 的提供商 | 我们据此接入 D，核对上游认证、参数和响应 |
| F-02：我们云端服务的 API 文档 | 我们 | B 据此调用 C，知道请求地址、参数、支付流程及返回内容 |

F-02 可以沿用 F-01 的参数，也可以根据我们对服务的包装采用不同格式；必须描述 C 实际接受的格式。不能直接用 F-01 替代 F-02，导致 Codex 请求上游、遗漏 x402 或使用错误参数。

F-02 至少包含：服务用途与地址、请求方法和路径、参数名称及含义与示例、必要认证要求、地点转换或澄清规则、x402 付款处理与约定限额、成功响应和单位说明，以及常见错误与处理方法。付款要求中的具体网络、资产、金额和收款地址仍由客户端按实际 402 报价核对。

优先采用最简单的交付方式：先提供本地 F-02 文件；云端部署时可一并提供可读取的文档地址。若放到服务器，拟将说明文档设为无需付费即可读取，以便 B 在购买前了解服务。每次独立天气查询开始前保存文档读取记录；文档与实际接口一起更新，避免使用过期说明。

**四、“使用现成工具”与“我们自己的工作”的边界**

我们复用的是 x402 客户端、支付中间件或网关、钱包工具、结算服务及天气数据接口。我们负责根据 F-01 接入 D，配置 C 的服务地址、参数映射、收费规则、收款地址和部署环境，编写并提供 F-02，验证 B 阅读文档后完成请求与交易的整条流程。

最终验收必须通过我们部署的服务地址完成。官方演示服务可以辅助学习或排查，但不能作为本项目最终卖方的替代品。

优先通过配置完成包装和接入。如果某个实际接口确实需要少量适配代码，再明确用途与工作量；不预先承诺所有组件完全无需调整，也不为增加原创代码而重写成熟功能。

本阶段定位为**基于接口文档驱动的 x402 天气服务应用集成与交易验证**。官方已经提供天气收费示例，因此仅将天气 API 与 x402 结合，不足以主张技术原创性。[2] 按 mentor 当前回复落实 A／B／C／D 与两份文档的关系，后续如有额外创新要求，再明确具体能力。

**五、技术选择：便利性优先原则与候选方案**

天气接口、云平台和测试链已按实施便利性选定。最终实测组合如下；后文候选表保留实施前的选择依据。

| 项目 | 最终采用与验证结果 |
|---|---|
| 天气来源 D | MET Norway Locationforecast 2.0 compact，无需上游 API 密钥；返回最近时次的真实模型预报，保留时间、单位与署名 |
| 地点转换 | Open-Meteo/GeoNames 核实北京首都记录，坐标按 F-02 保留四位小数 |
| 买方 B | 本机 Codex 阅读 F-02 后调用官方 x402 Fetch/ EVM SDK；钱包签名留在本机 |
| 卖方 C | Cloudflare Workers 上的自有 `yoyo-x402-weather`，官方 x402 Hono 中间件接入天气适配 |
| 支付 | x402 V2 exact，Base Sepolia 测试 USDC，每次 0.001；公共 facilitator 实际结算成功 |
| 部署与交付 | 已认领的 Accessible Trip 账号；公网文档、免费检查、收费查询及独立查账均已验证 |

实际公网地址为 `https://yoyo-x402-weather.accessible-trip.workers.dev`。完整版本、公开钱包、交易与余额见验收报告。未接入 RapidAPI、Finch 或候选网关 Tollbooth。

选择时优先考虑整套系统的操作成本：

1. **天气接口容易接入：**F-01 和请求示例清楚、参数简单、认证步骤少、可直接取得真实天气响应；结合地名或坐标的转换成本核实使用条件与额度，优先采用成本低且适用于本演示的接口。
2. **云端容易部署：**优先利用已有账号和匹配现成组件的部署模板，减少服务器维护、证书配置和重复注册操作；同时保证本机能够稳定访问服务。
3. **测试链容易验证：**买方、卖方和结算服务有配套支持，测试币容易领取，交易与余额容易查询；测试币领取或组件兼容性成为障碍时，可以改选其他兼容测试链。
4. **组件组合容易跑通：**先比较现成客户端、卖方组件和云环境能否直接配合，再锁定组合。网关和云平台一起选，不先固定某个工具再增加部署适配工作。

记录最终选择及简短理由，优先完成一套最小可运行系统。免费额度只是选择因素之一，不以“免费”代替可用性和使用条件核对。

| 项目 | 建议与选择依据 | 实施前核实事项 |
|---|---|---|
| 天气来源 | 选择文档清楚、认证与参数配置简单、可获取真实数据的天气 API；RapidAPI 作为候选，不设优先绑定 | F-01、实际请求地址、地名或坐标要求、地点转换方式、请求头、密钥要求、使用条件、额度和调用权限 |

| 卖方组件 | 比较现成配置式网关与官方中间件的整体接入成本；Tollbooth 保留为候选，其文档提供上游接入和 Docker 部署说明。[2][5] | 与客户端、云平台、测试链和 facilitator 的实际兼容性，以及是否需要额外适配 |

| 支付方式 | 建议按次固定金额，采用组件支持的 exact 方式。[2] | 客户端、卖方和结算服务使用兼容的版本与参数 |
| 单次价格 | 拟定 0.001 测试 USDC | mentor 可调整；执行前确认单笔上限、调用次数与总测试预算 |
| 收款方 | 独立卖方测试钱包 | 不能误填买方地址或其他链的资产配置 |

天气 API 的网页调试入口与实际 API 请求地址需要区分。当前不把提供的 RapidAPI 网页 URL 当作程序最终调用地址。

Finch 仅参考 API 请求格式。本方案不安排 Finch 注册、钱包连接、市场上架或平台接入；其页面能否访问不影响主流程推进。实际请求字段以最终选定天气接口的文档为准，不直接照搬 Finch 的字段。

链上采用测试币；云平台和上游 API 是否有资源费用，需按实际账号与套餐核实。这里只作成本核对，不预先购买资源。

**六、一次成功交易的执行顺序**

1. A 用自然语言提出具体天气需求，无需提供 C 的请求格式。
2. B 读取 F-02，确定地点与其他必要信息，按文档获取所需参数；缺少信息时先询问，不发起无依据的付费请求。
3. 记录用户原话、F-02 版本、最终查询参数、服务地址、测试时间及双方测试代币初始余额。
4. B 通过客户端向 C 发起未携带付款凭证的天气请求。
5. C 返回 HTTP 402 及付款要求，包含价格、资产、网络和收款信息。
6. 买方核对服务地址、网络、资产、收款地址与约定金额；符合要求才使用测试钱包签名。
7. 客户端携带支付凭证再次请求，C 通过结算服务处理验证与链上结算，并根据 F-01 接入 D。
8. C 向 B 交付真实天气数据及可关联的支付回执，记录本次交易哈希。
9. 查询交易状态、代币转账事件及双方余额，核对付款人与收款人、金额和报价一致。
10. B 用自然语言向 A 解释天气结果，给出查询地点、数据来源、支付金额与链上证据。

以上描述资源交付和支付的验收顺序。上游天气 API 在中间件内部具体何时被调用，按最终选定组件核实；方案要求只有付款成功才能向买方释放受保护的天气结果，不把未经验证的内部执行顺序写成事实。[2][3]

钱包签名只是授权；验证通过也不等于已经到账。必须取得成功的链上结算证据。[3] 如果付款结果不确定，先查回执和链上状态，再决定如何处理，避免因重复调用造成额外扣款。

**七、分步实施与每步产出**

| 步骤 | 工作内容 | 本步通过标准与产出 |
|---|---|---|
| 1. 选择便利的实施组合 | 按便利性选择 D、云平台、测试链和配套组件；取得 F-01；检查地点转换路径、本机环境和账号；锁定可用版本 | F-01 来源、合法参数样例、组件与部署选择表，以及选择理由 |
| 2. 验证原始天气 API | 根据 F-01 直接调用 D，确认认证、参数、数据时间与单位 | 一份有效天气响应，排除权限错误和写死的示例数据 |
| 3. 准备买方与钱包 | 配置现成客户端，创建或选择两个专用测试钱包，领取测试代币，核对链与合约 | 两个不同公开地址、买方可用余额、明确的调用与支出范围；密钥留在本机安全配置 |
| 4. 包装 C 并编写 F-02 | 根据 F-01 配置上游接入；接入 x402；设置价格与收款地址；编写与实际接口一致的 F-02，并提供可读取文件或地址 | 未付款请求得到正确 402；B 可以读取 F-02，明确参数、地点处理、支付和响应格式 |
| 5. 文档驱动的本地支付联调 | A 用自然语言提需求；B 先读取 F-02，组织请求，调用客户端跑通一笔测试交易并查账 | 文档读取与参数转换记录、请求日志、成功天气响应、交易哈希与余额变化 |
| 6. 云端部署与复验 | 部署 C；配置 HTTPS、运行参数和密钥；更新 F-02 的公网入口；由自然语言需求重新完成一次交易 | B 读取更新后的 F-02，通过我们自己的公网地址完成交易并向 A 返回结果 |
| 7. 交付与演示 | 整理 F-01 接入依据、F-02 和部署说明，串联需求、文档、HTTP、天气和链上证据 | mentor 可按说明核对，用户能解释 A／B／C／D 与 F-01／F-02 的职责 |

本地联调是准备步骤，**云端交易复验通过才算完成第一阶段**。先验收本步再推进，发现天气接口或结算不兼容时，在本步定位原因后调整组件。

Codex 负责配置、接入、运行检查和材料整理；用户负责目标判断、账号登录、验证码及需要本人完成的钱包交互。私钥、助记词和 API 密钥不写入聊天、提交材料或公开仓库。

**八、验收标准与证据清单**

| 编号 | 验收标准 | 保存证据 |
|---|---|---|
| A1 | 卖方为我们实际部署的云端服务 | 服务地址、部署信息、带时间的运行日志 |
| A2 | A 用自然语言提需求，B 根据 F-02 组织出正确、可重现的请求 | 用户原话、文档读取记录、请求方法、路径、查询参数及必要的信息澄清记录 |
| A3 | 未付款触发收费要求 | 首次 HTTP 402、解码后的网络／资产／金额／收款地址；不只保存自动重试后的最终响应 |
| A4 | Codex 通过客户端驱动请求和付款 | 指令、工具调用记录和客户端日志；不以手工转账加独立免费查询替代 |
| A5 | 支付在约定测试链真实结算 | 成功交易哈希、正确代币合约、转账事件及链浏览器记录 |
| A6 | 买方扣款、卖方到账 | 双方同一代币的前后余额，以及与本次金额对应的转账记录 |
| A7 | 返回真实天气数据 | 成功 HTTP 响应、查询地点、天气字段、单位、数据来源与可取得的数据时间；缺少数据时间时如实注明 |
| A8 | 天气调用与交易能关联 | 支付回执中的交易哈希与链上记录一致；同一测试记录关联请求参数和天气响应 |
| A9 | F-01 支撑 C 对 D 的真实接入 | 原始文档来源、上游调用样例与 C 到 D 的参数映射说明 |
| A10 | F-02 由我们编写、可供 B 阅读并与 C 实际行为一致 | F-02 文件或地址、版本信息，以及按文档成功调用的记录 |

余额核对时，保证观测区间不混入其他该代币转账，并记录查询时间或区块。在没有额外同币种费用时，应满足：

```text
买方交易前余额 − 买方交易后余额 = 本次付款金额
卖方交易后余额 − 卖方交易前余额 = 本次付款金额
本次付款金额 = 402 报价 = 代币转账事件金额
```

如有额外费用，单独列明。交易可能由结算服务提交，因此除交易状态外，还需核对代币转账事件的实际付款与收款地址。[3]

补充检查：未付款访问仍应被拦截；本地验证中用无效支付凭证检查不会泄露天气内容或触发有效扣款。付款成功但天气失败、只有签名没有结算、以及只有固定天气样例，均不能通过验收。

**九、最终交付物**

- 可访问的云端天气服务 C，以及实际采用的原始天气 API D。
- F-01 的来源与接入依据，包含必要的参数映射说明。
- 我们编写的 F-02 完整 API 文档，作为可读取文件或服务器文档地址交付。
- 可由 Codex 调用的买方入口、必要配置和简明运行说明。
- 卖方服务配置、上游接入方式和部署说明；提交材料使用占位符代替密钥。
- 买方与卖方的公开测试地址、网络、资产和价格说明。
- 一次从自然语言需求开始的完整云端交易记录：需求、F-02 阅读、参数组织、请求／响应、天气结果、支付回执、链上记录与余额核对材料。
- 一份简短演示步骤，说明已完成能力、限制和仍待处理事项。

F-02 文档及阅读后正确调用属于正式交付；创建一个可安装的 Skill 不作为本阶段交付要求。仅手动拼出请求跑通接口，尚不能替代最终的自然语言需求演示。

**十、mentor 回复已明确的实施要求**

1. **参与方：**A 为用户，B 为其 Codex，C 为我们部署的云端服务，D 为原始天气 API。
2. **上游接入：**我们根据 D 提供的 F-01 完成 C 到 D 的接入。
3. **对外说明：**我们编写 F-02；可以沿用或调整 F-01 的格式，确保描述 C 实际接受的请求。
4. **文档可访问：**将 F-02 放在服务器或手动提供给 B；每次调用 C 前先阅读。
5. **验收起点：**A 用自然语言提出天气查询需求；不要求 A 自己写出 C 所需的参数格式。B 根据 F-02 组织请求，具体缺失信息按文档补充或澄清。

天气接口、云平台和测试链无指定限制，以及 Finch 仅参考请求格式，均已由用户明确，无需重复确认。
